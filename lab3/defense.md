## 1. Как собрать и запустить

**Прошивка** — проект STM32CubeIDE в `lab3/source` (`lab3.ioc`, цель STM32F427VITx).
Сборка: открыть проект в CubeIDE, Build (конфигурация Debug), прошить стенд через
программатор (Run → Debug/Run). Тактирование 180 МГц настраивает CubeMX-код в `main.c`.

**Клиент** — каталог `lab3/client`, только стандартная библиотека Python 3:

```bash
python clock_client.py COM5          # Windows; у FTDI-порта обычно суффикс B
python clock_client.py /dev/cu.usbserial-XXXXB   # macOS
python clock_client.py COM5 --log my.log         # свой файл журнала
python clock_client.py --self-test   # самопроверка без стенда (macOS/Linux)
```

Клиент открывает COM-порт, шлёт `PING`, сам открывает браузер со страницей часов.
Весь обмен пишется в `uart.log`.

**Хост-тесты прошивки** (календарь, протокол, отрисовка символа — без железа):

```bash
gcc -std=c11 -I source/Core/Inc -o test source/tests/test_proto.c \
    source/Core/Src/clock.c source/Core/Src/proto.c \
    source/Core/Src/gfx.c source/Core/Src/font.c && ./test   # печатает ok
```

## 3. Архитектура

```
ПК (клиент)                          Стенд SDK-1.1M, STM32F427VI
┌────────────────────┐  UART 57600   ┌──────────────────────────────────┐
│ clock_client.py    │  8N1          │ main.c → app_init/app_poll       │
│  ├ serial_port.py  │◄─────────────►│  ├ uart.c   (очереди, HAL)       │
│  ├ protocol.py     │  PING/GET/SET │  ├ proto.c  (разбор команд)      │
│  ├ server.py       │  TIME         │  ├ clock.c  (календарь, формат)  │
│  └ static/ (стр.)  │               │  └ i2c.c (400 кГц, PB8/PB9)      │
│  журнал: uart.log  │               │      ├ rtc.c   → MCP79411 0x6F   │
└────────────────────┘               │      ├ oled.c  → SSD1306 0x3C    │
                                     │      └ pca9538.c → 0x70 (сброс)  │
                                     └──────────────────────────────────┘
```

Главный цикл — только `app_poll()`: разбирает готовые строки UART; раз в секунду
(сравнение `HAL_GetTick()`) читает RTC, при изменении показаний отправляет кадр
на дисплей и шлёт клиенту `TIME`. Блокирующих ожиданий в цикле нет — все события
либо уже произошли (байты в очереди UART), либо наступают по времени.

Потоки данных:
- UART RX: прерывание → очередь (64 байта) → `read_uart()` собирает строки до `\n` → `proto_parse` → ответ через `uart_write` → очередь TX (256) → прерывание.
- RTC: `rtc_read()` раз в секунду → `clock_view_t` (время, дата, день недели, состояние, валидность) → рисование и `TIME`.
- Дисплей: текст рисуется в буфер 1024 байта (`gfx.c`) → `oled_flush()` шлёт кадр по I2C.

Перерисовка — только при изменении показаний (`clock_view_same`) или после
неудачной отправки кадра (`display_ok`):

```c
static void present(void)
{
	if (display_ok && clock_view_same(&current, &drawn))
		return;
	draw_current();
	display_ok = oled_flush();
	if (display_ok)
		drawn = current;
}
```

## 4. Теория

### 4.1 Интерфейс I2C

**Физика.** Две линии: SCL (такты) и SDA (данные). Обе — open-drain: устройство
умеет только притянуть линию к нулю; единицу дают внешние подтяжки к питанию.
Отсюда свойство «монтажного И»: единица на линии только если её не тянет никто.
На стенде шина общая — на ней висят все устройства сразу.

**Скорости.** Standard 100 кГц, Fast 400 кГц (наш режим), Fast-plus 1 МГц.
Тактирование I2C1 идёт от APB1 (45 МГц при ядре 180 МГц).

**Адресация.** 7-битный адрес устройства + бит направления R/W образуют адресный
байт. HAL STM32 принимает адрес уже сдвинутым (8 бит, младший бит 0), поэтому в
коде адреса на бит левее «даташитовских»: 0x6F → `0xDE`, 0x3C → `0x78`,
0x70 → `0xE0`, 0x71 → `0xE2`.

**Транзакция.** START (SDA падает при высоком SCL) → адресный байт → ACK ведомого
→ байты данных, каждый подтверждается приёмником → STOP (SDA растёт при высоком
SCL). Запись в «регистр» устройства: START, адрес+W, номер регистра (указатель),
данные (указатель автоинкрементится), STOP. Чтение: START, адрес+W, номер
регистра, **повторный START**, адрес+R, данные, STOP — так HAL делает
`HAL_I2C_Mem_Read`.

**Подтверждения.** ACK — приёмник тянет SDA в ноль на 9-м такте. NACK —
отсутствие подтверждения; по нему HAL возвращает ошибку (так мы узнаём, что
устройство не отвечает, например дисплей отключён).

**Stretching.** Ведомый может держать SCL низким, «растягивая» такт, пока не
готов. В конфигурации растяжение разрешено (`NoStretchMode` = disable).

**Фильтры.** Аналоговый фильтр глушит короткие выбросы на линиях; включён,
цифровой выключен — как рекомендует пособие.

**Конфликты доступа.** Шина одна, и два «источника транзакций» не должны работать
одновременно. Здесь транзакции генерирует только главный цикл (блокирующий HAL с
таймаутом 50 мс, кадр — 200 мс): секундное чтение RTC и кадр дисплея идут
последовательно в одном контексте. Обработчик USART6 и SysTick шину не трогают.
Поэтому пересечений нет — это случай опроса из методички; расписание транзакций
по таймеру строить не потребовалось.

**Восстановление шины.** Если транзакция оборвалась, ведомый может остаться
держащим SDA в нуле, и мастер не сможет выдать START. Стандартный приём: отдать
SDA/SCL под ручное управление (GPIO open-drain), тактировать SCL до девяти
импульсов, пока SDA не отпустится (ведомый досматривает оставшийся бит и
«выравнивается» на границу байта), затем сформировать STOP и инициализировать
I2C заново. В коде — `i2c_bus_recover()`, вызывается раз после первой неудачной
попытки, потом попытка повторяется.

### 4.2 Часы реального времени MCP79411

**Что такое RTC.** Отдельная микросхема со своим кварцем 32 768 Гц: счёт секунд
не зависит от ядра, его кода и питания стенда (есть вход резервной батареи).
Микроконтроллер время не считает — только читает/пишет регистры.

**Регистры** (адреса автоинкрементятся, читаются одной транзакцией с 0x00):

| Регистр | Что | Заметные биты |
|---|---|---|
| 0x00 SEC | секунды BCD | бит 7 — **ST** (старт осциллятора) |
| 0x01 MIN | минуты BCD | — |
| 0x02 HOUR | часы BCD | бит 6 — формат 12/24 (у нас 24) |
| 0x03 WKDAY | день недели 1–7 | бит 3 — **VBATEN**, бит 5 — **OSCRUN** |
| 0x04 DATE | день BCD | — |
| 0x05 MONTH | месяц BCD | бит 5 — флаг високосного года у чипа |
| 0x06 YEAR | год BCD (00–99) | — |

**BCD** — каждая десятичная цифра в полубайте: 27 → `0x27`. RTC хранит так,
потому что счётчик десятичный по построению; в коде есть `bin_to_bcd` /
`bcd_to_bin` (последний отвергает невозможные полубайты > 9).

**День недели** — «свободное» поле 1–7: чип его не выводит из даты, его задаёт
программист. У нас 1 = понедельник.

**Установка времени — почему с остановом.** Пока часы идут (ST = 1), регистры
меняются сами, и многошаговая запись могла бы попасть «под ногу» тика. Поэтому:
1) читаем ST и пишем SEC с ST = 0 (останов); 2) записываем блок MIN…YEAR одной
транзакцией (в WKDAY добавляем VBATEN — резервное питание от батареи разрешено);
3) пишем SEC = BCD(сек) | ST — часы стартуют ровно с заданной секунды. Если шаг
2 не удался, ST возвращается как было (rollback в `rtc_set`).

**Чтение — защита от разрыва (tearing).** Семь регистров читаются не мгновенно:
секунда могла смениться посреди чтения, и время собралось бы из двух разных
секунд. После чтения блока перечитываем регистр секунд; не совпало — читаем блок
заново (до 3 попыток).

**Состояния** (то, что требует задание показывать):
- RUN — ST = 1 и OSCRUN = 1: генератор идёт;
- STOP — ST = 0: часы остановлены;
- ERR — ST = 1, но OSCRUN = 0 спустя 2 с после установки (генератор не завёлся),
либо шина не ответила, либо в регистрах не BCD. На дисплее — `RUNNING`/`STOPPED`/
`ERROR`, в протоколе — короткие `RUN`/`STOP`/`ERR`.

После установки OSCRUN поднимается не мгновенно, поэтому 2 секунды после `SET`
такое состояние считается идущим (льгота, `startup_pending`), чтобы статус не
мигнул ERR.

**Валидация.** `clock_fields_ok` — общая для парсера `SET` и разбора регистров:
часы 0–23, мин/сек 0–59, день недели 1–7, год 0–99, день 1 – длина месяца
(29 февраля — только в год, кратный 4; для двух цифр года, т.е. 2000–2099, этого
правила достаточно: 2000 делится на 400). Невалидное или нечитаемое →
`clock_view_invalid` → на дисплее и в клиенте `--:--:--`, состояние ERR.

### 4.3 Дисплей: модуль стенда и SSD1306

**Железо.** OLED 128×64 с контроллером SSD1306 на адресе 0x3C (`0x78` в HAL).
Линия сброса дисплея (RES#) идёт не к МК, а к выходу P0 расширителя PCA9538
(адрес 0x70): чтобы сбросить дисплей, надо написать регистры расширителя по той
же шине I2C. Сброс — импульс P0: единица → 0 на 1 мс → единица, пауза.

**PCA9538** — 8-битный расширитель GPIO по I2C. Регистры: `0x00` INPUT (чтение
выводов), `0x01` OUTPUT (уровни), `0x02` POLARITY (инверсия), `0x03` CONFIG
(1 = вход). Для сброса P0 настраиваем выходом (пишем `~0x01` в CONFIG) и дёргаем
OUTPUT. Второй расширитель стенда (0x71) обслуживает матричную клавиатуру — это
бонус, его мы не делали.

**Память дисплея (GDDRAM).** 128×64/8 = **1024 байта**. Память страничная:
8 страниц по 8 строк; байт — столбец внутри страницы; младший бит байта — верхний
пиксель столбца. Читать её по I2C нельзя, поэтому буфер кадра держим в ОЗУ МК
(`gfx.c`, 1 КБ), рисуем там и отправляем целиком.

**Управляющий байт.** Каждая посылка SSD1306 начинается с управляющего байта:
бит 6 (D/C#) различает команды и данные. `0x00` — «дальше команды», `0x40` —
«дальше данные». Окно записи задают команды `0x21` (столбцы 0–127) и `0x22`
(страницы 0–7); режим адресования горизонтальный (`0x20 0x00`): после конца
столбца указатель прыгает на следующую страницу. Поэтому кадр уходит одной
транзакцией: `0x40` + 1024 байта.

```c
bool oled_flush(void)
{
	static uint8_t packet[1 + GFX_BUFFER_SIZE];

	if (!i2c_master_write(OLED_ADDR, window_cmd, sizeof(window_cmd), 50))
		return false;
	packet[0] = 0x40;
	memcpy(packet + 1, gfx_framebuffer(), GFX_BUFFER_SIZE);
	return i2c_master_write(OLED_ADDR, packet, sizeof(packet), 200);
}
```

**Инициализация** (одна транзакция с `0x00` и списком команд, по таблице
пособия):

| Команда | Смысл |
|---|---|
| `0xAE` | дисплей выключен на время настройки |
| `0x20 0x00` | горизонтальный режим адресования |
| `0xC8` | реверс направления развёртки COM |
| `0xA1` | реверс порядка сегментов (ориентация под панель стенда) |
| `0x81 0xFF` | контраст максимум |
| `0xA6` | нормальный режим (не инверсия) |
| `0xA8 0x3F` | мультиплекс на 64 строки |
| `0xA4` | показывать содержимое RAM (не «всё включено») |
| `0xD3 0x00`, `0x40` | сдвиг строки 0 |
| `0xD5 0xF0` | частота кадров / делитель генератора |
| `0xD9 0x22` | фазы предзаряда |
| `0xDA 0x12` | альтернативная распиновка COM (для 128×64) |
| `0xDB 0x20` | уровень VCOMH |
| `0x8D 0x14` | внутренний зарядовый насос включён (без него OLED не светит) |
| `0xAF` | дисплей включён |

**Время передачи кадра.** Каждый байт в I2C — 9 тактов (8 данных + ACK):
1025 байт × 9 ≈ 9236 тактов / 400 000 Гц ≈ **23 мс**. Транзакция блокирует
главный цикл на это время, но не приём UART — байты копит обработчик прерывания.
Кадр отправляется только если показания изменились (`clock_view_same`) или
предыдущая отправка не удалась (`display_ok`), т.е. в обычном режиме — раз в
секунду.

**Графика.** Шрифт font8x8 (public domain): 8 байт на символ, печатные ASCII
32–126. Время рисуется масштабом 2 (символ 16×16) — 8 символов ровно закрывают
ширину 128 пикселей; дата, день недели и состояние — масштабом 1, по центру.

### 4.4 UART

**Кадр.** 8 бит данных, без чётности, 1 стоп-бит (8N1), 57600 бод. Параметры
задаёт CubeMX-код (`MX_USART6_UART_Init`), выводы PC6/PC7 в AF8. При 57600 бод
байт с обрамлением ≈ 174 мкс; строка `TIME ...` (29 байт) ≈ 5 мс.

**Драйвер.** Задание разрешает один из двух вариантов — выбраны **прерывания**
(USART6_IRQn, приоритет 0):
- приём: HAL держит приём одного байта, по завершении прерывание кладёт байт в
  кольцевую очередь (64) и перезапускает приём;
- передача: очередь (256), прерывание по завершении байта забирает следующий;
- если очередь передачи полна, `uart_write` ждёт места — терять ответ нельзя, а
  строки короче очереди;
- ошибки линии останавливают приём HAL, поэтому в `HAL_UART_ErrorCallback` приём
  запускается заново — иначе после первой ошибки консоль замолкает.

Кольцевой буфер — один писатель, один читатель (из ЛР2): писатель двигает head
после записи байта, читатель — tail после чтения; пустота = индексы равны, полнота
= следующий за head совпал с tail (поэтому полезная ёмкость на 1 меньше массива).
Обращения к индексам из прерывания и из цикла атомарны по одному байту, поэтому
запреты прерываний нужны только на время проверки-и-старта передачи.

Опросный режим из ЛР2 остался как запасной (прерывание USART6 выключено, чтение —
«забрать, если есть»). Протоколом он не переключается: задание требует одного
варианта.

### 4.5 Таймеры (раздел целей работы)

Классификация таймеров STM32F4 (RM0090):
- **Basic** TIM6/TIM7 — только генерация триггеров/DAC, без выводов;
- **General-purpose** TIM2–TIM5 (16/32-бит, захват/сравнение, ШИМ, энкодер),
  TIM9–TIM14 (упрощённые);
- **Advanced** TIM1/TIM8 — ШИМ с комплементарными выходами, защита;
- **SysTick** — системный таймер ядра Cortex-M, 1 мс, даёт `HAL_GetTick()`.

В этой работе от таймеров используется **только SysTick**: тик секунд сравнением
с `HAL_GetTick()`. Отдельные таймеры не нужны: время ведёт MCP79411 со своим
кварцем, и прерываний от TIM, которые генерировали бы I2C-транзакции, нет — это
и снимает вопрос планирования шины (см. 4.1).

### 4.6 Протокол обмена

Текстовый, ASCII, строка = сообщение, конец — `\n`. `\r` на стенде игнорируется.
Строки собираются в буфер на 80 байт; пустая строка после пары CRLF не отвечает,
переполнение буфера — `ERR` вместо выполнения команды.

| ПК → стенд | Стенд → ПК | Смысл |
|---|---|---|
| `PING` | `PONG`, затем `TIME` | проверка связи сразу после открытия порта |
| `GET` | `TIME` | запросить время |
| `SET HH:MM:SS DD/MM/YY W` | `OK` + `TIME`, при ошибке `ERR` | установить время; W = 1–7, 1 = понедельник; год — 2 цифры |
| — | `TIME` раз в секунду | стенд сам репортит состояние |

Формат `TIME`: `TIME HH:MM:SS DD/MM/YY W RUN|STOP|ERR`. Недостоверные показания:
`TIME --:--:-- --/--/-- 0 ERR`.

`TIME` шлётся без запроса раз в секунду — так клиент всегда видит актуальное
время и состояние, и «пульс» стенда виден и в журнале. Даты проверяются дважды:
на клиенте (до отправки) и на стенде (одной функцией с разбором регистров RTC).

### 4.7 Клиентская программа

Только стандартная библиотека Python 3. Модули:
- `serial_port.py` — COM-порт средствами ОС: Win32 API (`CreateFileW` + DCB +
  таймауты) на Windows, termios на macOS/Linux; чтение блоками с таймаутом.
- `protocol.py` — сборка/разбор строк, календарь (длина месяца, високосность),
  разбор значений формы.
- `server.py` — отдельный поток читает порт и режет поток байтов на строки;
  состояние платы — объект под мьютексом, который поток UART обновляет, а
  HTTP-обработчики читают копию; `ThreadingHTTPServer` на localhost со случайным
  свободным портом; журнал.
- `static/` — страница часов: крупное поле времени с платы, поля даты/времени/
  дня недели, кнопки «Установить» и «Установить текущее»; опрос состояния
  примерно 5 раз в секунду.

Журнал — по строке на сообщение: `ГГГГ-ММ-ДД ЧЧ:ММ:СС.ммм DIR текст`, DIR ∈
{TX, RX, NOTE}. Пример: `2026-11-25 16:49:07.123 RX TIME 09:05:03 27/10/26 2 RUN`.

После открытия порта сразу уходит `PING`; если `PONG` не пришёл за 1,5 с, в окне
предупреждение (обычно это не тот COM-порт). Кнопка «Установить текущее» берёт
время ПК. `--self-test` без стенда проверяет календарь, сборку/разбор строк и
петлю UART через псевдотерминал (pty — macOS/Linux).

## 6. Вероятные вопросы и ответы

**— Почему транзакции I2C не конфликтуют?**
Все транзакции выполняет главный цикл в блокирующем режиме HAL с таймаутом: они
строго последовательны. Прерывание USART6 и SysTick шину не трогают. По методичке
это опросный вариант, для него конфликтов не бывает по построению; «расписание»
транзакций по таймеру не потребовалось, потому что прерываний от TIM нет.

**— UART-байты пришли во время передачи кадра (23 мс) — что с ними?**
Ничего: их заберёт обработчик USART6 и положит в кольцевую очередь приёма.
Главный цикл разберёт их, когда вернётся из `oled_flush`.

**— Что будет, если дисплей отключить?**
`oled_flush` вернёт ошибку, экран не обновляется, но часы и обмен живут: попытка
отправки повторяется при следующем изменении показаний. Если шина зависнет (SDA
прижат ведомым), сработает восстановление: 9 тактов SCL вручную + STOP + ре-init.

**— Что если RTC не отвечает или отдаёт мусор?**
`rtc_read` вернёт невалидное представление → на дисплее и у клиента
`--:--:--`, состояние ERR; `SET` вернёт `ERR`.

**— Почему при записи времени нужно останавливать генератор?**
Пока ST = 1, регистры тикают сами, и запись блока из шести регистров могла бы
пересечься с приращением времени. Остановили (ST = 0) → записали блок → записали
секунду с ST = 1: старт ровно с заданного значения.

**— Зачем повторное чтение регистра секунд?**
Семь регистров читаются не атомарно: если тик случился посреди транзакции, время
соберётся из двух секунд. Повторное чтение секунд обнаруживает такой разрыв —
блок читается заново.

**— Что такое BCD и зачем он тут?**
Две десятичные цифры в байте (27 = 0x27). RTC хранит десятичные счётчики в BCD;
на границе — перевод в бинарное и обратно с проверкой полубайтов ≤ 9.

**— Почему адрес 0xDE, если в даташите 0x6F?**
HAL ждёт 8-битный адресный байт с нулевым битом R/W: 0x6F << 1 = 0xDE. То же с
0x3C → 0x78 и 0x70 → 0xE0.

**— Зачем байты 0x00/0x40 перед посылкой на SSD1306?**
Это управляющий байт контроллера: бит D/C# говорит, идут дальше команды (0x00)
или данные видеопамяти (0x40). Кадр = 0x40 + 1024 байта одной транзакцией.

**— Как устроена память дисплея?**
Страничная: 8 страниц × 128 столбцов, байт = столбец страницы, младший бит —
верхний пиксель. Окно записи задают команды 0x21/0x22, в горизонтальном режиме
указатель сам идёт по столбцам и страницам.

**— Почему буфер кадра в ОЗУ МК?**
GDDRAM SSD1306 по I2C только пишется, читать её нельзя; поэтому кадр собирается
в своём буфере (1 КБ), и отправка — побайтно точная копия буфера. Бонус: можно
рисоваться в буфер сколько угодно, шина не задействуется.

**— Сколько времени занимает обновление дисплея?**
1025 байт × 9 тактов / 400 кГц ≈ 23 мс. Обновление только при изменении
показаний — раз в секунду.

**— Как определяются состояния часов?**
STOP — бит ST = 0. RUN — ST = 1 и OSCRUN = 1. ERR — ST = 1, но генератор не
поднялся спустя 2 с после установки, либо шина/BCD не сошлись. Первые 2 с после
`SET` считаем идущими (OSCRUN поднимается с задержкой).

**— Почему время считает RTC, а не таймер микроконтроллера?**
У MCP79411 свой кварц 32 768 Гц и резервная батарея (VBATEN): время живёт без
прошивки и питания МК, точность — кварцевая. Счёт на SysTick умер бы при
перезагрузке и плывёт от частоты ядра.

**— Какие таймеры STM32F4 вы знаете, что использовали?**
Basic TIM6/7, general-purpose TIM2–5 и TIM9–14, advanced TIM1/8, плюс SysTick
ядра. В работе — только SysTick (1 мс, `HAL_GetTick`), прерываний от TIM нет.

**— Прерывания или опрос для UART?**
Задание требует выбрать один вариант — выбраны прерывания с кольцевыми очередями
из ЛР2: главный цикл не ждёт байт, приём и передача по байту в прерывании.
Опросный режим остался как запасной. Отдельно следим: ошибки линии останавливают
приём HAL, поэтому приём перезапускается в обработчике ошибок.

**— Что при переполнении буферов?**
Очередь передачи не переполняется молча: `uart_write` ждёт места (ответы короче
очереди). Приёмная очередь при переполнении теряет байт, но приём перезапускается.
Строка длиннее 80 байт не выполняется — стенд отвечает `ERR`.

**— Как клиент понимает, что связался со стендом?**
Сразу после открытия порта шлёт `PING`; `PONG` означает связь. Нет `PONG` за
1,5 с — предупреждение в окне (обычно не тот COM-порт).

**— Зачем журнал, что в нём?**
Требование задания: все данные обмена в файл с меткой времени. Формат строки:
метка с миллисекундами, направление TX/RX (NOTE — служебное), текст. Годится для
разбора сбоев после факта.

**— Почему интерфейс в браузере — это допустимый GUI?**
Это графический интерфейс: окна/поля/кнопки, ввод текста и нажатия. Командной
строкой клиент не является; TUI тоже не нужен.

**— Как проверяются даты?**
На клиенте и на стенде: длина месяца, 29 февраля только в год, кратный 4, часы/
минуты/секунды в диапазонах, день недели 1–7. Для двух цифр года (2000–2099)
правило «кратен 4» полно: 2000 делится на 400.

**— Что за clock stretching? Используется?**
Ведомый удерживает SCL низким, пока не готов отдать/принять байт. Контроллер
STM32 это поддерживает, растяжение у нас разрешено (`NoStretchMode` disabled);
явно мы его не используем, это свойство протокола.

**— Почему аналоговый фильтр включён, цифровой выключен?**
Как рекомендует пособие: аналоговый глушит короткие выбросы без настройки,
цифровой программируемый здесь не нужен.

**— Матричная клавиатура?**
Бонусное задание, не выполнялось. Расширитель клавиатуры (PCA9538, 0x71) на шине
есть, драйвер чтения клавиш и антидребезг для него мы не писали.
